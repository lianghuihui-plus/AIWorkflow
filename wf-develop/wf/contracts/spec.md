# 产物契约：output/specs/T-XXX.md

## 路径

`output/specs/T-XXX.md`

## 必需章节

- `# T-XXX — {任务标题}`
- `## 审核状态`
- `## 任务概述`
- `## 依赖`
- `## 关键行为`
- `## 实现方案`
- `## 修改点`

## 修改点格式

`## 审核状态` 必须符合 `contracts/review-status.md`。新生成或修订后的规格状态必须为 `待审核`；只有用户确认后才能改为 `已确认` 并进入对应任务的代码实现。

```markdown
### 修改点 1：{摘要}

- **文件：** `path/to/file.ext` [NEW]
- **类型：** 新增
- **位置：** {类/函数/区域，新文件可省略}
- **内容：** {编码指令}
- **约束：** {约束}
```

## 编号规则

- 修改点序号从 1 开始递增。
- 修改点必须按序号升序排列。
- 新增修改点时追加到 `## 修改点` 末尾，并使用下一个序号；不要插到已有修改点顶部。

## 质量规则

- `output/design.md` 中每个任务都必须有一份规格文件。
- 审核状态必须存在，且进入代码实现前必须为 `已确认`。
- 既有文件路径必须在代码仓库中确认。
- 新文件必须标注 `[NEW]`。
- 不得使用“待确认”等模糊占位；遇到不确定项应写入实现阶段问题。
- 关键行为必须来自或可追溯到 `output/analysis.md`。
- 修改点只允许描述业务源码、配置、资源、接口和数据结构变更，不得指向单元测试、集成测试、测试夹具或其他测试代码文件。
- 修改点不得要求新增或修改测试类、测试方法、测试用例、Mock 或断言；所有测试代码由 `generate-tests` 阶段负责。
- 关键行为可以描述正常路径、边界条件、异常处理和状态变化，但不得指定测试框架、测试文件或测试实现方式。
- 为提升可测试性而进行的业务源码改造可以作为修改点，但必须指向业务源码并说明生产职责，不得写成测试代码修改。
