# 需求分析

## 要解决的问题

理解 PRD 真正要改变的业务行为，形成足以支撑技术设计的整体需求认识，而不是改写原文或填写固定模板。

## 建议关注

- 目标用户、业务目标、成功标准与现状问题是否一致。
- 核心流程、异常流程、降级行为、生命周期和跨模块影响。
- 明示范围、非范围、兼容边界、数据与性能约束。
- 多份输入之间的冲突、术语差异、遗漏和未经证实的假设。
- 原始依据是否能通过任务包中的来源路径追溯。

根据需求复杂度自由组织 Markdown。优先解释关键行为及其原因，避免把主要篇幅用于流程字段或框架说明。

## 最低交付内容

产物必须覆盖目标与背景、范围与非范围、关键行为、已确认约束、原始依据，以及冲突、缺失和合理推断。结果清单只保留需求索引与候选记忆增量，不复制正文。

## 必须停止的情况

只有某个未知选择会实质改变范围、关键行为、安全边界或后续技术方向，并且无法从现有事实可靠推导时，才停止并提交阻塞问题。能够明确标注且不妨碍设计的未知项写入风险或假设，不阻塞流程。
